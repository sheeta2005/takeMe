# 小区助老项目压测与参数验证

## 测试对象和口径

按 2500 名老人、250 名志愿者、25 名管理员建立隔离合成账号。业务假设是单小区、单 JVM、单 MySQL，不将注册人数当作并发人数。

压测机器为 Windows、16 个逻辑处理器、约 15.7GB 内存。后端、JMeter、MySQL、Redis、RabbitMQ 共用本机，数据不能直接当作独立线上服务器的容量承诺。

后端使用 Java 21.0.7，JMeter 5.6.3。数据库、Redis 和 RabbitMQ 均与原开发数据隔离。两组配置的 JVM 参数都为 `-Xms512m -Xmx1024m -XX:+UseG1GC`，没有靠增加堆大小、降低 BCrypt 强度或关闭鉴权制造收益。

隔离库初始生成 101000 个订单、202000 个服务项，其中 100000 个历史订单是只读容量占位数据，不是逐笔模拟完成的真实服务流水。1000 个候选订单的预约时间在每轮开始刷新；测试交易保留在隔离库中。

## 负载模型

| 场景 | 虚拟用户数 | 目标 HTTP 请求速率 | 每轮时长 |
| --- | ---: | ---: | ---: |
| 常规 | 60 | 30 RPS | 10 分钟 |
| 高峰 | 300 | 180 RPS | 10 分钟 |
| 突发 | 600 | 360 RPS | 10 分钟 |

主操作覆盖目录、订单列表、详情、消息、志愿者候选订单、管理员看板和建单。建单还有相同请求重试、模拟支付、取消、退款及状态检查。使用 0.5 至 1.5 秒思考时间；目标吞吐与实际达到的吞吐分开报告。

HTTP 成功须同时满足业务码成功；重试须返回同一订单 ID；取消须得到状态 5。预签名 Token 只用于已登录业务，密码登录另测。

最终参数进行同一 JVM 上六段各 10 分钟的持续运行：常规、高峰、突发、高峰、高峰、常规。另有预热；不是“额外固定高峰压测 60 分钟”。全程保持 600 条真实 WebSocket 连接和正常心跳，结束后检查在线统计归零。

## 选定配置

| 参数 | 选定值 | 业务和测量依据 |
| --- | --- | --- |
| Tomcat 最大/最小空闲线程 | 80 / 10 | 同机筛选中保持吞吐，减少线程占用 |
| Tomcat 接收等待队列 | 100 | 有界排队，避免请求无限堆积 |
| Tomcat 最大连接数 | 2000 | 为 600 条推送连接和 HTTP 连接留余量 |
| Druid 最大活跃连接 | 16 | 单小区规模和本轮数据库需求，不盲目增大数据库并行度 |
| Druid 等待连接上限 | 3000ms | 有界等待，防止连接耗尽时长期阻塞 |
| MQ 每个监听器最小/最大消费者 | 1 / 3 | 不丢通知，减少空闲消费线程 |
| MQ 每个消费者预取数 | 20 | 限制未确认消息量，正式测试还需验证积压 |
| JVM 堆和收集器 | 512MB 至 1GB，G1 | 基线与调参组保持一致 |

配置文件为 `takeMe/server/src/main/resources/application-community.yml`。数据库凭据仍在本地或外部配置中，不写入该文件。Redis 使用既有 Lettuce 连接复用，不新增池；MySQL 全局连接上限和缓冲池、BCrypt 强度 12 均未调整。

结论是：当前社区参数在本机隔离环境下可以支撑常规 30 RPS 与高峰约 165 RPS，业务错误为 0；但 600 虚拟用户、目标 360 RPS 的突发阶段不达标，实际只有约 190 RPS，出现 58 个失败请求。不能对外宣称“600 并发突发稳定通过”。

突发失败构成如下：管理员聚合看板读超时 24 次，志愿者可接服务读超时 9 次，老人订单列表读超时 3 次；老人订单列表业务码 500 共 9 次，志愿者可接服务业务码 500 共 6 次，取消后状态校验未完成 2 次，取消与退款获取 JDBC 连接失败 2 次，另有 3 次鉴权文本为空。突发期间主机 CPU 采样最高 100%，可用内存最低约 703MB，Outbox 待发送峰值 1624 条、最老待发送 226 秒；后续高峰阶段待发送逐步恢复，最终快照显示 Outbox 全部已发送。

资源时序摘要已经脱敏写入 `docs/loadtest-measurements.json`。阶段峰值为 30 秒采样点，不代表捕获所有瞬时峰值。最终数据库一致性检查：`mq_outbox` 全部 status=1，重复 `(user_id, request_id)` 为 0，父单取消但子项未取消或服务项已分配但志愿者为空的记录为 0。GC 日志无 Full GC 或 OOM，最大暂停约 71.08ms。

发布回归为 96 项：75 项通过、21 项旧演示默认跳过、0 失败、0 错误。前端构建通过，但保留原有较大产物分块警告，没有为本任务扩展打包重构。

真实 HTTP 的建单、同请求重试、模拟支付、志愿者接单、取消链路通过；取消推送到达时通知已持久化。恢复启动时曾有历史待发送事件，第一次推送功能检查超过 10 秒等待窗口；待发送消化为 0 后复测通过。不能把这次检查说成推送 P95 或上线延迟保证。

密码登录另测：同一 IP、30 个线程、300 个独立账号，BCrypt 强度 12，正常账号及 IP 限流。`release-login-clean` 无 Arthas 监听，结果为 300 请求、0 错误、25.23 RPS、平均 735.86ms、P95 1350ms、P99 1471ms、最大 1581ms。这是约 12 秒的短登录峰值，不是持续登录容量。`release-login` 同时进行 Arthas 配置验证，不能作为干净对比轮次。

Arthas 4.3.5 已在发布构建实际附加：未认证 HTTP 401，认证后的 `thread -n 3` 与 `jvm` 均成功，端口 3658/8563 只监听 127.0.0.1。验证后执行 `stop` 并确认监听端口消失；最终持续压测另启新 JVM，没有附加 Arthas。

## 参数结论

最终采用的 `application-community.yml` 参数面向“常规与高峰稳定”，不是极限突发：

| 参数 | 最终值 | 结论 |
| --- | --- | --- |
| Tomcat 最大线程 | 80 | 高峰约 165 RPS 无错误；突发 600VU 时会排队，不再继续下调 |
| Tomcat 最大连接数 | 2000 | 足以同时容纳 600 条推送连接和 HTTP 连接 |
| Druid 最大活跃连接 | 16 | 高峰阶段够用；突发阶段有 JDBC 连接获取失败，说明 360 RPS 突发已超出本配置目标 |
| Druid 最大等待 | 3000ms | 让连接压力在突发下较快暴露，不让请求无限等待 |
| MQ 消费者并发 | 1 至 3 | 高峰可恢复；突发出现待发送积压，不能声称通知链路无压力 |
| MQ 预取 | 20 | 降低单消费者未确认消息量；结果显示极端突发仍需更多消费者或削峰策略 |

若要把 600VU、360RPS 作为硬性指标，需要单独开“突发容量”优化分支，重点压测数据库连接池、管理员看板聚合 SQL、志愿者候选列表查询、Outbox 消费并发和压测机资源隔离。当前最小改造不应为了单机突发压测盲目把默认连接和线程调大。

## 结论边界

本轮不是生产真实流量回放，也不是最大容量搜索。容量测试没有为了吞吐绕过预约时间窗口，开始服务和完成服务由功能及数据库回归验证。单次推送验证不能推出全体消息的推送延迟分位数。

仍需真实用户验收、独立部署压测、TLS、备份恢复、监控告警和生产账号权限配置。既有 WebSocket 连接的立即踢出、全局 JWT 撤销、多节点在线统计和真实支付对账不在本次最小改造范围，不能宣称已经实现。

## 当前目标配置变更

历史压测仍按清单中的 `-Xms512m -Xmx1024m -XX:+UseG1GC` 解释。后续正式环境目标 JVM 参数调整为 `-Xms1024m -Xmx1024m -XX:+UseG1GC`，需要重新压测后才能形成新的容量结论。

正式环境 Redis 参考配置调整为 `maxmemory 64mb`、`maxmemory-policy allkeys-lru`；本次不修改专用压测 Redis，历史压测数据不能证明该淘汰策略在正式环境下的行为。由于 Redis 同时承担缓存和限流，限流键存在被淘汰的可能，严格限流场景需要单独 Redis 实例。
