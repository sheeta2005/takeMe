# 消息队列修缮

## 上线顺序

1. 已有 Outbox 表的环境，先执行 `docs/migrations/20261020_mq_failed_message.sql`，再执行 `docs/migrations/20261021_mq_retention.sql`，创建归档表、结案字段和清理索引。两份迁移均可重复执行，不删除已有记录。
2. 发布并启动应用，确认 `takeme.consumer.failed.queue` 归档消费者正常运行。新版归档写入依赖结案字段，不能省略迁移。
3. RabbitMQ Management 插件可访问且应用已声明全部 11 个队列后，执行以下脚本。首次设置或下调容量时应暂停发布、等待管理统计刷新并核查积压；统计预检不能替代并发发布控制。

```powershell
./tools/rabbitmq/apply-queue-policies.ps1 `
  -Username $env:TAKEME_RABBITMQ_USERNAME `
  -Password $env:TAKEME_RABBITMQ_PASSWORD `
  -VirtualHost $env:TAKEME_RABBITMQ_VIRTUAL_HOST
```

脚本先检查队列是否齐全、统计是否可用，以及现有积压是否超过拟设上限，通过后写入 8 个策略。所有队列均设置条数、消息体字节数上限和 `reject-publish`，不再使用淘汰旧消息的 `drop-head`；更新同名策略会移除旧策略中的通知溢出死信路由。无需删除重建现有队列。

写入后逐队列检查策略名称、生效值及冲突的声明参数；策略接口不是批量事务，中途失败时应修复原因后重新执行。部署必须将脚本非零退出码作为失败处理，不能只以应用成功启动作为容量已经生效的依据。后续可用相同参数加 `-VerifyOnly` 只校验、不修改策略；该模式用于部署后或重启后的容量核查。

|---|---:|---:|---|
| `notification.user.queue` | 30000 | 64 MiB | `reject-publish` |
| `notification.volunteer.queue` | 30000 | 64 MiB | `reject-publish` |
| `notification.admin.queue` | 30000 | 64 MiB | `reject-publish` |
| `approval.admin.queue` | 2000 | 16 MiB | `reject-publish` |
| `approval.result.volunteer.queue` | 2000 | 16 MiB | `reject-publish` |
| `notification.broadcast.queue` | 100 | 8 MiB | `reject-publish` |
| `order.create.delay.queue` | 5000 | 32 MiB | `reject-publish` |
| `order.cancel.dlx.queue` | 5000 | 32 MiB | `reject-publish` |
| `volunteer.start.timeout.delay.queue` | 1000 | 8 MiB | `reject-publish` |
| `volunteer.start.timeout.queue` | 1000 | 8 MiB | `reject-publish` |
| `takeme.consumer.failed.queue` | 5000 | 64 MiB | `reject-publish` |

通知容量按 2500 位老人各积压约六条订单状态事件并留两倍余量估算；审批按 250 位志愿者各四次申请并留两倍余量；群发按 25 位管理者各两条任务并留两倍余量。容量为初始预算，需结合生产期 `messages_ready`、`message_bytes_ready` 和压测排空时间复核。两种上限先触发者生效，字节数只计算消息体，不是 Broker 内存总量上限。

队列长度不统计已投递未确认的消息。应用默认 `prefetch=20`，结合最大消费者数约束此部分规模；小区部署每个业务队列最多 3 个消费者，对应每个应用实例每队列最多预取约 60 条，失败归档消费者固定为单消费者、预取 1 条。多实例需按实例数累计。

满载时生产者收到 NACK，现有发布确认逻辑将其视为失败，Outbox 保持待发送并退避重试。广播可能部分分支已经接收，重试必须保留原事件 ID，消费端继续依赖事件幂等，不能将 NACK 理解为所有分支均未接收。失败归档入口满载时，恢复投递失败必须保留原业务消息等待重试。

## 失败消息处置

- 重试三次后，消费者将原消息发布到 `takeme.consumer.failed.queue`，并写入来源队列及异常信息。消费者原消息只在失败消息队列收到发布确认后才会 ACK。
- 归档消费者原样保存消息体和消息头；归档失败则退避并重新入队。数据库迁移必须先于新版应用启用。
- 管理员可通过 `GET /api/admin/mq-failures` 分页查看归档，`GET /api/admin/mq-failures/recent-counts` 查看最近一分钟按队列和失败类型的聚合告警。
- 修复原因后，通过 `POST /api/admin/mq-failures/{id}/replay` 定向重放至原队列，不经过原广播交换机。未知来源消息不能自动重放。状态 `1` 表示 Broker 已确认接收，不代表业务处理成功；重放后的业务异常会再次归档并将状态设回待处理。
- 核查业务已恢复或确认无需处理后，通过 `POST /api/admin/mq-failures/{id}/close` 提交 JSON 字段 `reason`，说明结案依据（去除首尾空白后 1 至 1000 字）。待核查和已重投记录均可人工结案，记录结案管理员、时间、原因，状态变为 `2`。已结案记录不能再次重放；列表支持 `status=2` 筛选并返回结案信息。
- 再次收到同一事件的消费失败时，归档重新开放为状态 `0`，清空当前结案信息；重放、结案共用行锁，清理时同时检查结案状态和时间，避免与重新归档发生竞争时误删。
- 接口继承 `/api/admin/**` 管理员登录鉴权。通知落库复用事件 ID 去重；重放审批、订单和超时业务前仍需检查对应业务状态。

## 数据保留与清扫

应用清理任务启动 1 分钟后开始执行，随后每小时执行一次，不依赖 MQ 启用开关。

- `mq_outbox`：只删除状态 `1`、最后确认更新时间早于 7 天前的记录。创建时间很早但刚补发成功的记录仍完整保留 7 天，状态 `0` 不自动删除。
- `mq_failed_message`：只删除状态 `2`、人工结案时间早于 30 天前的记录。状态 `0`、`1` 均不自动删除，也不以重试次数或创建时间代替结案依据。
- 每张表每轮最多 10 批，每批最多 500 条，按保留时间和主键排序，每批使用独立事务且事务超时 5 秒。失败批次回滚，已提交批次保留，下一轮继续清扫。边界时间采用严格早于，恰好达到截止时间的记录留待下一轮。
- 配置位于 `mq.cleanup`：`outbox-retention-days`、`failed-retention-days`、`batch-size`、`max-batches`，均须为正数。默认每张表每小时最多删除 5000 条，应按生产终态新增速率调整，使长期清理能力覆盖终态增长。
- 通过 `mq.alert` 配置积压告警：Outbox 待发送达到 10000 条或有消息滞留超过 10 分钟；失败消息按状态 `0`、`1` 分组，任一组达到 1000 条或有记录超过 24 小时未处置时，每分钟聚合记录告警。状态 `1` 从最后重投时间计时，状态 `0` 从最近失败时间计时。

未发送和未结案数据仍可能在长期故障中持续增长。保留未完成消息与数据库绝对容量上限不能同时仅靠清理任务保证；若需要绝对上限，须另行明确业务入口暂停规则。普通 InnoDB 删除主要回收表内可复用空间，不保证立即缩小磁盘上的表文件。

历史延时队列仍使用 RabbitMQ 默认到期死信转发，目标队列不可用或满载时存在丢失窗口，不能将到期转发视为可靠交付承诺。当前新订单、新接单不再生产此类 TTL 事件；订单和服务项超时由数据库扫描任务复核并处理，保留该兜底。RabbitMQ 的这一限制见[官方死信文档](https://www.rabbitmq.com/docs/dlx)。

## 验证记录

2026-10-21 在 MySQL 8 和 RabbitMQ 3 的隔离测试环境执行全量回归：共 184 项，163 项通过、21 项旧演示测试按原条件跳过，失败和错误均为 0。数据库测试仅复制业务表结构到随机测试库，消息测试使用随机虚拟主机，不清理业务记录或业务队列。

覆盖迁移重复执行及记录保留、确认时间与保留期边界、分批清理限额及事务回滚、结案与重新归档、重放与结案竞争、条数及消息体字节上限、广播部分接收后的事件 ID、失败队列满载后的原消息保留，以及容量脚本的漏队列、超限预检、重复执行和策略漂移。

在 `takeMe` 目录执行以下命令可复验；需先通过测试环境变量 `TAKEME_TEST_MYSQL_PASSWORD`、`TAKEME_TEST_RABBIT_PASSWORD` 提供测试凭据，默认账号分别为 `root`、`admin`。测试账号须有创建、删除隔离测试库或虚拟主机的权限，本地 MySQL 需已有 `takeme` 表结构，RabbitMQ 需启用 Management 插件；Windows 下还会实际调用 PowerShell 容量策略脚本。

```powershell
mvn -pl server -am test "-Dtakeme.mysql.tests=true" "-Dtakeme.rabbit.tests=true"
```
