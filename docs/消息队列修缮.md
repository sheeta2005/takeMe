# 消息队列修缮

## 上线顺序

1. 在业务数据库执行 `docs/migrations/20261020_mq_failed_message.sql`，创建失败消息归档表。
2. 发布并启动应用，确认 `takeme.consumer.failed.queue` 归档消费者正常运行。
3. RabbitMQ Management 插件可访问且应用已声明队列后，执行：

```powershell
./tools/rabbitmq/apply-queue-policies.ps1 `
  -Username $env:TAKEME_RABBITMQ_USERNAME `
  -Password $env:TAKEME_RABBITMQ_PASSWORD `
  -VirtualHost $env:TAKEME_RABBITMQ_VIRTUAL_HOST
```

脚本以策略设置可在线调整的队列长度、overflow 和通知死信路由，可重复执行，无需删除重建现有队列。通知、审批、群发和管理员审计队列溢出的旧消息会路由至统一失败归档队列；延时任务和超时业务队列在满载时拒绝新发布。应用经 Outbox 直接发布的消息由发布确认和 Outbox 重试承接；Broker 的到期死信转发不在 Outbox 的重试边界内。

## 容量

| 队列 | 上限 | 满载策略 |
|---|---:|---|
| `notification.user.queue` | 30000 | `drop-head`，转失败归档 |
| `notification.volunteer.queue` | 30000 | `drop-head`，转失败归档 |
| `notification.admin.queue` | 30000 | `drop-head`，转失败归档 |
| `approval.admin.queue` | 2000 | `drop-head`，转失败归档 |
| `approval.result.volunteer.queue` | 2000 | `drop-head`，转失败归档 |
| `notification.broadcast.queue` | 100 | `drop-head`，转失败归档 |
| `order.create.delay.queue` | 5000 | `reject-publish` |
| `order.cancel.dlx.queue` | 5000 | `reject-publish` |
| `volunteer.start.timeout.delay.queue` | 1000 | `reject-publish` |
| `volunteer.start.timeout.queue` | 1000 | `reject-publish` |
| `takeme.consumer.failed.queue` | 5000 | `reject-publish` |

通知容量按 2500 位老人各积压约六条订单状态事件并留两倍余量估算；审批按 250 位志愿者各四次申请并留两倍余量；群发按 25 位管理者各两条任务并留两倍余量。人数只用于初始缓冲预算，需结合生产期 `messages_ready` 和压测排空时间复核。队列长度只统计待投递消息，不含已投递未确认的消息。

## 失败消息处置

- 重试三次后，消费者将原消息发布到 `takeme.consumer.failed.queue`，并写入来源队列及异常信息。消费者原消息只在失败消息队列收到发布确认后才会 ACK。
- 归档消费者原样保存消息体和消息头；归档失败则退避并重新入队。数据库迁移必须先于新版应用启用。
- 管理员可通过 `GET /api/admin/mq-failures` 分页查看归档，`GET /api/admin/mq-failures/recent-counts` 查看最近一分钟按队列和失败类型的聚合告警。
- 修复原因后，通过 `POST /api/admin/mq-failures/{id}/replay` 定向重放至原队列，不经过原广播交换机。未知来源消息不能自动重放。状态 `1` 表示 Broker 已确认接收，不代表业务处理成功；重放后的业务异常会再次归档并将状态设回待处理。
- 接口继承 `/api/admin/**` 管理员登录鉴权。通知落库复用事件 ID 去重；重放审批、订单和超时业务前仍需检查对应业务状态。

`drop-head` 在通知队列满载时会淘汰最旧的待消费消息；将其路由到失败队列仅表示进入人工处置链路，不表示原业务已完成。队列上限不是吞吐承诺，需监控积压和失败归档增长。

现有队列使用 RabbitMQ 默认死信转发，目标队列不可用或满载时仍存在丢失窗口，不能将溢出归档或到期转发视为可靠交付承诺。上线需核查失败归档队列及两个超时消费队列的积压；RabbitMQ 的这一限制见[官方死信文档](https://www.rabbitmq.com/docs/dlx)。
