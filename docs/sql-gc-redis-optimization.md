# SQL、GC 与 Redis 优化复盘

本文记录 2026 年 10 月 5 日的真实诊断与最小改动。对象为 2500 名老人、250 名志愿者、25 名管理员的小区单 JVM 服务。压测库为 `takeme_loadtest_20261004`，Redis 为专用 6381 实例；没有修改真实业务库，也没有改共享开发 Redis。密钥、合成 token 和带凭据的运行日志不进入 Git。

## 一、上一轮结果和本轮诊断

上一轮正式持续测试的六个阶段及接口统计保存在 `docs/loadtest-measurements.json`。不能把其概括为“全场景通过”：突发阶段只有约 190 RPS，58 个失败，P95 5464 ms，P99 6869 ms。常规与高峰阶段没有业务错误。

Arthas 在独立诊断请求中使用 `watch SimpleExecutor.doQuery` 和业务方法 `trace`，不与计分压测同时运行；只记录 SQL 模板，不记录老人姓名、手机号或鉴权 token。诊断文件在被 Git 忽略的 `tools/results/optimization-before`。

诊断确认：

| 问题 | 证据 | 最小处理 |
| --- | --- | --- |
| 老人列表 N+1 | 一页 10 条：COUNT、主列表、10 次服务项查询 | 只取本页订单 ID，批量查询服务项 |
| 志愿者列表 N+1 | 每个服务项再查父订单及老人 | 本页父订单、老人各批量查询一次；保留每条记录只含一个服务项的语义 |
| 待接订单时间条件 | `CONCAT(service_date,' ',service_time)`；COUNT 需要回表访问候选项 | 改日期范围及时间上下界，添加覆盖候选筛选和父订单关联的索引；跨午夜回归 |
| 分页边界 | `pageSize=-1` 可绕过分页；只按时间排序不能保证同秒记录顺序 | 参数限 1～100，非法参数返回 400；热点列表按 `create_time,id` 稳定排序 |
| 冷看板重复扫描 | 5 次订单 COUNT；单次诊断业务方法约 1.06 秒 | 合并为一次条件聚合，并给“今日”增加次日上界 |
| 支付聚合全表访问 | OR 跨 `payment_time/refund_time`；执行计划扫描 102345 行，单次约 468 ms | 收款、退款独立聚合并相减，增加各自覆盖索引，保留模拟净收款口径 |
| 缓存过期并发回源 | 原切面未进行双重检查与回源合并 | 单 JVM 固定 64 条锁条带，与目录主动失效协调 |

执行计划是诊断采样，不是接口 P95。Arthas 增强、SQL 缓冲状态与当时主机负载都影响单次耗时；不得把这些单次数据包装成严格线上性能承诺。

## 二、为什么不调整 GC

本轮历史诊断时参数为 Java 21 G1：`-Xms512m -Xmx1024m -XX:+UseG1GC`。当时没有增加堆，也没有凭经验添加年轻代比例、暂停目标或 GC 线程数。之后按用户要求，应用启动目标改为 `-Xms1024m -Xmx1024m -XX:+UseG1GC`；这是后续配置变更，未用旧压测结果冒充新参数的性能验证。JMeter 负载发生器的堆配置不随应用参数变更。

对正式持续测试的 GC 日志与 58 个失败请求进行时间交集统计：

| 指标 | 实测 |
| --- | --- |
| 清单时长 | 3891 秒 |
| Young GC | 2125 次，约 0.55 次/秒 |
| 全部记录到的暂停 | 2143 次 |
| 累计暂停 | 9435.35 ms |
| 最大暂停 | 71.075 ms |
| 暂停时长占比保守上界 | 0.242% |
| Full GC | 0 |
| OOM、to-space exhausted、Evacuation Failure 日志 | 0 |
| GC 后堆最大占用 | 284 MB |
| 失败请求期间累计重叠暂停最大值 | 45 ms |

日志包含启动及预热，因此上述暂停占比是保守上界，不是 GC CPU 百分比。这个证据支持“GC 停顿无法解释本次数秒失败”，不支持“GC 完全没有 CPU 或分配开销”。本轮优先减少查库次数、对象装配和并发冷回源，而不是扩大堆掩盖数据库压力。

上一轮同时记录到整机 CPU 100%、可用物理内存约 703 MB、数据库连接获取失败和通知积压。属于资源竞争的证据，但没有同步火焰图或逐请求连接等待数据，不能断言全部失败只有一个根因。Outbox 每轮最多 20 条、间隔约 1 秒且同步发布，也是积压可能的来源；本轮不借 SQL 优化扩大 MQ 改造范围。

复现脚本：`tools/loadtest/analyze-gc.ps1`。完整逐请求交集在 `tools/results/optimization-gc.json`，该文件带原日志 SHA256。

## 三、Redis 缓存设计与边界

### 缓存用途

- 缓存可重建的服务目录和管理看板，减少重复查询。
- 使用短窗口 Lua 限流保护登录和下单；限流计数不是普通可任意淘汰的缓存。
- 不缓存订单详情、支付真值或账号可用状态，不使用 Redis 分布式锁协调 MySQL 订单事务。

### 穿透

目录只有 0～4 五个合法类型，控制器先拒绝非法类型，不为无限无效整数建空缓存。查询返回空列表时，空列表本身可缓存；返回 null 时保留短期空值哨兵。命中空列表或空值不再查询数据库。

当前有限键空间没有引入布隆过滤器：不存在需要预加载海量对象 ID 的业务。非缓存订单详情仍按所属人检查数据库，不能声称所有接口都靠空缓存抵御任意恶意流量。

### 击穿

单 JVM 使用固定 64 条锁条带；miss 后加锁再检查缓存，由一个线程回源，其余复用结果。锁条带数量固定，不按每个陌生 key 无限制创建锁对象。目录提交后的主动失效与回源写缓存共用同一锁，防止旧查询在失效之后重新写入旧目录。

这是本机并发合并，不是多实例互斥。若未来多 JVM 部署，需要重新评估多实例冷回源和失效协调，不能将本方案说成分布式一致性方案。

### 雪崩与故障

保留原注解分钟语义，实际 TTL 加减 10% 随机抖动：

| 缓存 | 原基准 | 新实际 TTL |
| --- | --- | --- |
| 服务目录 | 2 分钟 | 108～132 秒 |
| 看板汇总 | 1 分钟 | 54～66 秒 |
| 看板趋势、分布 | 30 分钟 | 1620～1980 秒 |
| null 哨兵 | 2 或 5 分钟 | 108～132 或 270～330 秒 |

Redis 读写或序列化失败时，只对查询缓存降级为数据库回源，不重复执行数据库查询、不吞掉数据库业务异常。目录修改后缓存失效失败时保留已提交的修改，以短 TTL 恢复；缓存不提供实时强一致保证。

抖动减少同时到期；回源合并减少热点重复查询，但不等于解决 Redis 全实例宕机时所有接口的容量问题。Redis 整体不可用时仍需数据库容量、入口限流和运维恢复，本轮没有伪造故障演练通过结果。安全限流不因缓存降级而默认放行。

### 内存淘汰与过期

优化前，专用压测 Redis 和共享开发 Redis 的实际配置都是：

- `maxmemory=0`：没有配置 Redis 内存上限。
- `maxmemory-policy=noeviction`：不是 LRU/LFU 淘汰，达到已设置的上限时拒绝写入。
- `hz=10`、`active-expire-effort=1`：保留原主动过期工作参数。
- 实测使用约 1.2 MB，RSS 约 11 MB，`evicted_keys=0`。不能把主机内存压力归因于它。

当前正式环境目标配置已按业务要求调整为 `tools/redis/community.conf` 中的 `64 MB + allkeys-lru`。这不是本轮历史压测的 Redis 配置，压测实例继续保持原 `noeviction`，因此不能用历史压测数据证明正式环境淘汰策略的表现。由于缓存与限流目前共用一个 Redis，`allkeys-lru` 也可能淘汰限流键，使限流窗口被提前重置；严格限流场景应拆分独立 Redis 实例。本次按最小改动只记录并采用正式策略。

过期和内存淘汰不同：业务键设置 TTL，Redis 在访问键时检查过期并通过后台主动检查清理；`allkeys-lru` 不会阻止 TTL 到期清理。不能把 `hz=10` 解读为每个键严格每 100 ms 删除。

开发共享实例保持不变，专用压测 Redis 也保持原配置。正式环境部署必须显式加载 `tools/redis/community.conf`；修改配置文件不会自动改变已经运行的 Redis 进程，需在正式发布时加载配置或通过运维变更执行并持久化。

全局 `keyspace_hits/misses` 同时包括限流、空值哨兵等命令，不能直接用于宣称业务缓存命中率。本轮没有凭这个数字包装“99% 缓存命中”。

## 四、分页与索引取舍

新增索引只围绕实测热点，迁移文件为 `docs/migrations/20261005_sql_performance.sql`，可重复执行。不删除原索引，不修改主键，不引入搜索引擎或新的分页协议。

老人列表先限定所属人：诊断时老人 1 只有 71 条订单，即使全库约 15 万条，深页不会扫描全库所有订单。新索引按 `user_id,create_time,id` 排序。保留页码和 COUNT 是因为前端要展示总量；普通居民页规模不值得强行改成游标。

待接订单 COUNT 仍与候选数相关；日期索引不是“所有情况下消除 filesort”，因为筛选时间与列表排序时间不同。管理员超深分页、模糊订单号搜索、数据大幅增长后仍需重新压测，必要时再使用游标或更窄范围，不能声称本轮消除了所有深分页成本。

支付两个覆盖索引增加存储与写入维护成本，但对应真实看板净收款业务；必须通过前后执行计划和混合写入复测确认收益，不能只因为“联合索引”是面试关键词就添加。

本轮实际进行了二次修正：最初索引仅覆盖各自时间列，MySQL 却在收款查询选择退款索引、退款查询选择收款索引；刷新统计信息和改用字面量时间后仍有大量回表。没有马上强制索引，而是给这两条新索引补齐另一时间列，保证交叉选择时依然覆盖查询。最终执行计划是 `Covering index lookup`，不再回表；收款及退款两段单次采样合计约 127.8 ms，原查询约 468 ms。记录中的 SQL 访问行数并未变成个位数：这批交易大多发生在同一天，仍需读取当期约 11 万条索引记录。只应表述为消除回表和减少计算成本，不能称“零扫描”。

中间错误计划、刷新统计后的计划及最终覆盖计划均保存在 `tools/results/optimization-after`；最终全套诊断在 `tools/results/optimization-after-final`。实际业务库和压测库的预约日期时间格式均只读检查过，未发现非 ISO 日期或非 `HH:mm` 时间；没有为优化清洗或删除历史记录。

## 五、验证与压测记录

本轮先新增缓存并发、TTL、异常降级和分页边界测试，原实现出现 3 个失败、2 个错误，保存于 `tools/results/optimization-red-tests.log`。随后增加批量查询、空页、真实 MySQL 聚合口径、跨午夜条件、稳定分页和目录回源/失效竞争测试。

正式短对照使用相同社区参数、原混合业务 JMX、600 条实际长连接、10 秒资源采样、60 秒预热及 180 秒突发。Arthas 在测量前停止；压测线程和目标吞吐不等于实际成功 RPS。JMeter 输出、每接口统计、GC、资源采样、构建哈希与数据规模均保留，不只摘取总平均响应时间。

最初两轮连接准备失败没有进入计分；客户端握手完成早于服务端在线登记时，等待实际计数到 600，未放宽成功标准。`optimization-before-clean` 与 Maven 测试编译有时间重叠，不用于干净的性能因果比较；重新安排 `optimization-before-controlled` 独立计分。

最终全量回归为 111 项：90 项执行成功、21 项既有演示跳过、失败为 0。完成支付索引的二次修正后，73 项相关 MySQL、缓存和订单专项测试再次全部通过。非法 `pageSize=-1/0/101` 的真实 HTTP 请求均返回 400；非法目录类型 999 不产生缓存键。

Arthas 实际 SQL 次数：

| 一页 10 条记录 | 优化前业务查询 | 优化后业务查询 | 加上鉴权的完整请求 |
| --- | --- | --- | --- |
| 老人订单列表 | 12 | 3 | 13 → 4 |
| 志愿者待接列表 | 22 | 4 | 23 → 5 |
| 冷看板 | 11 | 7 | 不把命中缓存误计为业务回源 |

冷看板额外验证：先删除专用 Redis 的单个看板键，再同时发起 20 个真实 HTTP 请求，20 个全部成功，Arthas 观察到代理调用 20 次、实际业务回源 1 次。批次耗时 387 ms，含诊断增强，不属于计分接口 P95。查看剩余 TTL 时目录为 118 秒、看板为 55 秒，符合抖动范围；剩余 TTL 不是创建时完整 TTL。

历史短压测使用的专用 Redis 实际为 `maxmemory=67108864`、`maxmemory-policy=noeviction`，本次没有修改压测实例；共享开发 Redis 仍是 `maxmemory=0`。正式环境目标则是 `64 MB + allkeys-lru`，两者必须分开表述。

### 尚未完成的验证

- 优化后只做了短突发复测，没有再次跑完 60 分钟持续测试；不能声称新的长期稳定性结论。
- 未演练 Redis 整实例宕机、达到内存上限及多 JVM 缓存协调；异常降级目前有单元测试，不能包装成真实故障演练。
- 共享开发 Redis 的无内存上限配置保留；正式部署需明确加载参考配置，索引迁移也尚未应用真实业务库。
- 管理员超深分页、模糊订单号、大幅增长的数据和消息 Outbox 更高吞吐需要另行验证；本轮没有扩大技术栈或顺手重构这些模块。
- 后续正式 Redis 参考配置改为 `allkeys-lru`、应用堆初始值改为 1024 MB；尚未操作正式服务器或重启现有应用，需区分配置文件修改与运行时生效。

## 六、面试可用表达

“我先按小区人口建立常规、高峰和突发场景，记录接口分位数、错误类型、CPU、数据库等待、GC 和消息积压。发现突发失败后，没有立即扩线程池或堆，而是将失败时间与 GC 停顿对齐，排除了长 GC 停顿解释。再用 Arthas 观察 SQL 调用次数、EXPLAIN ANALYZE 检查访问方式，确认列表 N+1 和冷看板聚合扫描。保留单 JVM 架构，只批量装配本页数据、改可索引条件、合并重复统计，并为有限缓存补并发回源合并和 TTL 抖动。历史压测 Redis 保留 noeviction；正式环境按业务要求使用 allkeys-lru，同时明确它可能淘汰限流键，严格限流需要独立 Redis。优化效果只用实际复测指标表达，同时保留未复测的边界。”
